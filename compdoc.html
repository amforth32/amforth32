How it works · RV
Where isrstub puts a new frame

Every trap on RV QEMU starts with these four instructions (rv/isr.s:46–49):

	push s11                       # old s11 on the interrupted RS
	bgeu s5, s11, 1f               # task: all of ISR_stack is free
	mv   s11, s5                   # handler: s5 is the first free address
1:	addi s11, s11, -TF_SIZE

The rule. Each new frame goes into free space, just below whatever stack is in use. On entry s11 points at the current handler's frame, or at the top of ISR_stack when no handler is running. s5 is the return stack pointer of the code that was interrupted. Which of the two marks the free space depends on what was interrupted:

  • A task. Its return stack lies above ISR_stack, so all of ISR_stack is free and the frame goes at s11, its top.
  • A handler. Its return stack is inside ISR_stack, just below its own frame. From s11 down to s5 is in use: the handler's return-stack entries and the s11 just pushed. Below s5 is free. s5 is the first free address, so the frame goes there.

Why the push comes first. push s11 moves s5 down 4 bytes and stores the old s11 there. In the handler case the saved s11 is then part of the in-use range, and s5 already marks where the free space starts, so mv s11, s5 needs no adjustment. In the task case the saved s11 goes on the task's own return stack. Either way (exiti) pops it from the same place, with s5 back at its value after the push.

Why bgeu s5, s11. At this point no register is free: apart from s11, every register still holds the interrupted code's value, and none can be saved until the frame exists. Reading in-isr? would need a register to load it into. Comparing s5 with s11 needs none: s5 at or above s11 means a task was interrupted, s5 below s11 means a handler. MIE is 0 from the trap until the handler runs +int, so nothing can interrupt these four instructions.

What it relies on. The comparison is only right if every task return stack lies above ISR_stack. core/amforth32.s allocates ram_vector, then ISR_stack, then the task blocks (lines 10–21), so today it holds: ISR_stack ends at 0x80040904, and TASK0's return stack starts at 0x800409f0. The .if at the end of rv/mcu/qemu/amforth.s stops the build if a change ever breaks it. If it were broken, an interrupted task would look like a handler: its frame and the handler's return stack would go on the task's own return stack (only 160 bytes for TASK0), and would overflow into whatever lies below it.

ARM has no such step. In handler mode the CPU always uses MSP, which already points into ISR_stack, so a nested exception should land below the outer handler's stack without any test. ARM nesting is untested (see swi.plan). The second diagram in the walkthrough shows the RV result at the deepest point.

Test walkthrough · RV QEMU

The nested-interrupt test, step by step

tests/interrupts-rv-nested.fr runs on RV QEMU only (tests/tests.frt: #if defined(TARGET_RVQEMU) && !defined(IRQ_HAMMER)). The outer interrupt is the faux SysTick: slot 7 runs systick.isr, which runs the handler in slot 15. The inner interrupt is msip, the CLINT software interrupt, in slot 3. Indented steps happen inside the outer handler, and the more indented ones inside the inner handler. The addresses are worked out from the frame layout and match a manual run (ISR_stack is 0x80040504–0x80040904; the task's return stack is above it, at about 0x80040A74).

What a nested interrupt should do
Part 1: nesting allowed
  1. Set up-int -systick 0 msip ! save the old slot 15 handler; zero the counters

    Interrupts off, timer stopped, no software interrupt pending.

  2. Install the inner handler in slot 3:noname 0 msip ! 1 inner +! in-isr? @ idepth ! rp@ irp ! inside @ seen ! ;i 3 trap! 3 irq.on

    It clears msip first (the source stays pending until software clears it), then records its depth, its return stack pointer, and whether the outer handler was active.

  3. Install the outer handler in slot 15:noname 1 outer +! in-isr? @ odepth ! rp@ orp ! 1 inside ! +int 1 msip ! 0 inside ! ;i systick# trap!

    It records its depth and return stack pointer, marks itself active, allows nesting with +int, raises msip, then marks itself inactive.

    Why it ends without -int. From +int to ;i the handler runs with MIE = 1, and that is the window in which the inner interrupt may arrive. It doesn't have to close that window itself, for two reasons. First, (exiti) starts with csrci mstatus, 8, so MIE is 0 before mepc, mstatus and the registers are reloaded, and no interrupt can land half-way through the restore. Second, the interrupt state the task gets back doesn't depend on what the handler left in MIE: mret sets MIE from the MPIE saved in this handler's frame, which is the task's own MIE at the moment it was interrupted. A -int before ;i would be harmless, just pointless.

  4. Startrp@ rp0 ! systick.ms 1- systick! +systick +int 20 ms

    The task's return stack pointer is saved for the balance check. A 1 ms tick starts, and the task waits 20 ms.

  5. SysTick trap: isrstub, from the taskpush s11 (0x80040904, the top of ISR_stack) onto the task's return stack; s5 ≥ s11, so a task was interrupted: frame at 0x80040904 − 116 = 0x80040890; save registers, mepc, mstatus; in-isr? = 1; s5 = s11

    The CPU has already set MIE = 0 and MPIE = 1.

  6. Outer handler runs on ISR_stacksystick.isr re-arms mtimecmp, then runs slot 15; the two colon calls push down to 0x80040888

    It stores odepth = 1 and orp = 0x80040888, sets inside = 1, runs +int (MIE = 1), then 1 msip !.

  7. msip trap at once: isrstub, from a handlerpush s11 (0x80040890, the outer frame) onto the outer handler's return stack, at 0x80040884; s5 < s11, so a handler was interrupted: s11 = 0x80040884; frame at 0x80040884 − 116 = 0x80040810; save registers, mepc (a point inside the outer handler), mstatus; in-isr? = 2; s5 = s11

    Why at s5. This is the handler case of where isrstub puts a frame. From s11 (0x80040890) down to s5 (0x80040884) is in use: the outer handler's return-stack entries and the s11 just pushed. Below s5 is free, so s5 is the first free address, and the frame goes there. In step 5, the task case put the frame at s11, the top of ISR_stack.

  8. Inner handler runs0 msip ! inner +1 idepth = 2 irp = 0x8004080C seen = inside = 1

    Its one colon call pushes from 0x80040810 to 0x8004080C.

  9. Inner ;i → (exiti)MIE = 0; in-isr? = 1; mepc and mstatus from the inner frame; registers back (s5 = 0x80040884); pop s11 = 0x80040890; mret

    mret sets MIE from the saved MPIE (1) and returns into the outer handler just after 1 msip !.

  10. Outer handler finishes0 inside ! ;i → (exiti): MIE = 0; in-isr? = 0; mepc and mstatus from the outer frame; registers back (s5 = the task's return stack); pop s11 = 0x80040904; mret

    Back in the task, with MIE = 1 from the task's saved MPIE.

  11. Repeat for 20 ms, then check-int

    Each tick repeats steps 5–10. Then the checks:

    • inner @ 0>: the inner handler ran.
    • seen @ = 1: it ran while the outer handler was active.
    • odepth @ idepth @ = 1 2: in-isr? counted the nesting.
    • irp @ orp @ u<: the inner return stack is below the outer one.
    • orp @ rp0 @ u<: the outer handler ran on ISR_stack, not on the task's return stack.
    • rp@ rp0 @ =: the task's return stack is balanced.
    • in-isr? @ = 0: no handler is left running.
    • inner @ outer @ - abs 2 <: one inner per outer, with one tick of slack at the -int.

Open findings

Differences that still change behaviour

Gap · ARM
ARM's empty-slot path leaks

Slots start at 0 on both targets, but ARM's systick.init leaves SysTick counting with its interrupt enabled, and ARM has no irq.on to refuse it. As soon as anything runs +int without first installing a SysTick handler, each tick takes stub_exit, which leaves PSP 4–8 bytes lower and DEBUG_BREAK cleared. This is from reading the code; it hasn't been traced. interrupts-cortexm.fr now ends this way (its cleanup empties slot 15 with trap-), but with interrupts off. Fixing stub_exit would make an empty SysTick slot harmless.

Gap · ARM
in-isr? means nothing on ARM

The variable is shared, but only RV updates it. On ARM it always reads 0, even inside a handler (measured: a SysTick handler that stored in-isr? @ ran 4 times and saw 0 each time). Forth code that tests in-isr? will behave differently on the two targets. ARM could update it in isrstub and (exiti), or provide a word that reads IPSR.

Wart · RV
The trap-entry scheme is fixed in the source, and QEMU and CH32 are set up in very different ways

There is no build option that picks the scheme. Each target sets it in its own startup file, and the two files are not variants of each other.

RV QEMU: a .ifnb switch picks one of two standard schemes. rv/mcu/qemu/qemu.startup:47–54:

.ifnb 
	la t0, isrstub                 # direct mode, all traps enter here
	csrw mtvec, t0
.else
	la t0, _vector_base            # vector mode
    ori t0, t0, 1                  # MODE =1 (vectored)
	csrw mtvec, t0
.endif

.ifnb is true only when something follows it on the line. Nothing does, so the .else branch is built: vectored (standard RISC-V MODE = 1). The CPU jumps to _vector_base + 4 × code, and the j isrstub or j nullhandler instruction there runs next (rv/mcu/qemu/vectors.s). Put any token after .ifnb and you get direct mode (MODE = 0): every trap, interrupt or exception, enters isrstub.

Both branches use the same isrstub, (exiti) and ram_vector. isrstub reads mcause itself, so it works either way. What changes:

  • Exceptions: vectored sends them to table entry 0 (nullhandler); direct sends them to isrstub, which branches to _trap_exception.
  • Unwired codes: vectored stops them in the table; direct lets them reach the slot lookup.
  • vectors.s is assembled in both cases (amforth.s:28), so direct mode carries an unused table.

Both branches pass the test suite (WANT_IGNORECASE=1 TIMEOUT=10s make tests). Re-run on 26 Nov 2026 after the ISR_stack change, with the test files as updated that day plus the new nested test: PASS 689, FAIL 0 in both schemes (679 existing + 10 in interrupts-rv-nested.fr). Its T { typo is fixed, but the SysTick handler's 42 throw prints err# not known each tick, even though it is caught. That text lands in the middle of the echoed line, so results.awk doesn't recognise it as a test. The interrupt tests run SysTick through slot 7, and the nested test adds msip through slot 3, in both modes. No test raises an exception, so direct mode's _trap_exception path is untested.

CH32V307: one WCH-specific scheme, no switch. rv/mcu/ch32v307/307.startup:376–396:

.if WANT_NESTED_ISR
	li t0, 0x0b         /* enable nested and hardware stack */
	csrw 0x804, t0
.else
	li t0, 0x01         /* hardware stack only */
	csrw 0x804, t0
.endif

    /* WCH-specific: enable GINTENR (master interrupt gate) */
    li t0, 0x6088
    csrw 0x800, t0

    /* Enable floating point and interrupt */
   	li t0, 0x6088           
   	csrs mstatus, t0

 	la t0, _vector_base
    ori t0, t0, 2           
	csrw mtvec, t0

The only .if here selects nesting (WANT_NESTED_ISR), not the entry scheme. mtvec | 2 is a QingKe V4 extension: bit 0 = 0 means one entry for every trap, and bit 1 = 1 means that entry holds an address (standard RISC-V only allows an instruction). So every trap goes to .word _master_int. Around it, the scheme differs from QEMU at every step:

  • intsyscr (0x804) turns on HPE, which saves the caller-saved registers in hardware. _master_int saves only s1–s10 on s11, not QEMU's full 26-register frame.
  • _master_int, not isrstub, finds the slot. It uses mcause directly, with no PLIC (the PFIC numbers interrupts itself).
  • Slot 0 → it reads the same _vector_base table as data and jumps to the C/asm handler there. QEMU just returns.
  • Its own (exiti) (rv/mcu/ch32v307/words/exiti.s) restores s1–s10 and leaves the rest to HPE.

So "single handler" means two different things. QEMU's direct branch is standard RISC-V MODE 0 into the QEMU isrstub. CH32's is a WCH address-table entry into _master_int, with HPE behind it. Neither target can build the other's scheme. A per-target option, for example in config.inc, would replace QEMU's empty .ifnb with a named switch. Giving CH32 a vectored choice would also need a vector table that dispatches without _master_int. That is still to do.

Info
Smaller asymmetries

RV QEMU still allocates reg_shadow but no longer uses it. ARM's vector table stops at 15, so MPS2 peripherals have no interrupt path. On RV, slot 7 belongs to the faux SysTick while it runs, so 7 trap! has no visible effect. The RV test suite needs more than CI's 5 s timeout on this Mac (it passes with 10 s).

Gotchas

Things that catch you out

Gotcha
trap- empties a slot but leaves its source enabled

In Forth this is : trap- ( n -- ) cells trap.base + 0 swap ! ;. It is a shared word in core/ and doesn't call irq.off, for three reasons:

  • irq.off exists only on RV QEMU;
  • slot 15 on RV is reached only through systick.isr, so it has no source of its own;
  • ARM has no per-slot disable.

So turn the source off first (-systick, n irq.off), then n trap-. Otherwise a source that is still enabled traps into an empty slot: on RV QEMU a level-triggered source livelocks, and on ARM SysTick takes the leaking stub_exit path.

Note · RV
What an empty slot (XT = 0) does on RV QEMU: kept as is, on purpose

isrstub saves the full frame as for any trap, finds 0 in ram_vector[slot], and branches to _trap_return → _trap_restore in (exiti). No Forth runs, and in-isr? is neither incremented nor decremented. A PLIC claim, if any, is completed; mepc, mstatus and the registers are reloaded; the saved s11 is popped; then mret. The frame, the return stack and in-isr? come out balanced.

Nothing clears the cause, so the outcome depends on the source:

  • Timer (MTIP, slot 7), msip (slot 3), level-triggered PLIC device: still pending after mret, so it traps again at once. That's a livelock: the interrupted code never runs another instruction, nothing is corrupted, and nothing flags it.
  • One-off PLIC pulse, spurious claim (id 0), slot ≥ 64: returns normally; the event is lost.
  • Slot 15 (virtual SysTick): harmless. systick.isr in slot 7 has already moved mtimecmp, and its ?dup if execute then skips the empty slot.

Why it stays this way. This matches ARM as closely as the hardware allows. On both targets 0 means "no handler", and the stub returns without running Forth: ARM through stub_exit, RV through _trap_return. ARM's SysTick doesn't livelock only because the CPU clears its pending bit on entry. A level-triggered NVIC interrupt with an empty slot would livelock on ARM too. Rather than give RV a default handler that changes state behind the user's back, the words keep a 0 out of enabled slots:

  • trap! refuses 0 (throws −263 "no isr handler").
  • irq.on refuses to enable a slot that holds 0.
  • Slots are 0 at boot (_start clears ram_vector), and every source starts disabled (mie = 0).

A livelock is still possible in two ways: n trap- while source n is enabled (see the gotcha above), or enabling a source without irq.on, by writing mie or the PLIC registers directly. CH32 differs: there, 0 means "use the C/asm handler in the flash _vector_base table".

Note · RV
s11 grows down on QEMU (on ISR_stack) and up on CH32 (on reg_shadow)

The RAM layout is reg_shadow (256 B), then ram_vector (1 KB), then ISR_stack (1 KB), then the task blocks. Each target starts s11 at the end that matches its growth direction, so push, pop and initial value agree on both:

  • QEMU: s11 = RAM_upper_ISR_stack, grows down. Frames (116 B) and handler return stacks share ISR_stack; a nested frame goes below the outer handler's return stack. This relies on every task return stack lying above ISR_stack, which an assembler check at the end of rv/mcu/qemu/amforth.s enforces (see where isrstub puts a frame). Overflow runs down into ram_vector's top slots (255, 254, …).
  • CH32V307: s11 = RAM_lower_reg_shadow, grows up (_master_int stores, then adds 40). 40-byte frames (s1–s10, HPE saves the rest), room for 6. Overflow runs into ram_vector slot 0, 1, …. That needs 7 nested Forth handlers, and nesting is off (WANT_NESTED_ISR, "HPE only").

Neither target checks for overflow. Each target builds its own (exiti), so the pops stay matched to the pushes.

Stale clear loop in the CH32 startup. 307.startup:401–406 (and 203.startup) clear from ram_vector_base up to reg_shadow. The commented-out line above it (reg_shadow - 0x100 * cellsize) shows it was written when ram_vector sat below reg_shadow. With the current layout the start is above the end, so the loop clears slot 0 once and stops. It does no harm, because the bss loop has already zeroed both blocks, but it doesn't do what it says. To fix it, clear RAM_lower_ram_vector..RAM_upper_ram_vector as qemu.startup does, or delete the loop.
